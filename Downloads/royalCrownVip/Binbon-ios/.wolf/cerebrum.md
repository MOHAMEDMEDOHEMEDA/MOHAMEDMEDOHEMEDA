## Key Learnings

- **Clean-arch migration recipe (Group-2 / API-coupled feature → feature-first + dummy data)** — proven on Onboard [2026-06-15]. Per feature F: (1) `Features/F/{Domain/Repositories,Data/Repositories,Data/Models,Presentation/{View,ViewModel,Components}}`; (2) `mv` model→Data/Models, view→Presentation/View (subviews→Components), vm→Presentation/ViewModel; (3) Domain protocol returns ENTITIES — `Result<Model, APIError>`, action endpoints `Result<Void, APIError>` (NO BaseResponse); (4) Data repo is a dummy impl returning `.success(<dummy>)` with a `private extension Model { static let dummy }`; (5) DELETE the shared `Network/UseCase/<domain>/{<X>Repo,<X>Service}.swift` ONLY when F is its sole consumer — multi-consumer shared repos (ProfileRepo→Profile+Follow; SettingRepo→Notifications+Promote+Setting; AuthRepo→Auth+ForgetPassword) must have ALL consumers converted first, else name-collision; (6) rewire VM: inject protocol via `init(repo: Proto = ConcreteRepo())`, replace `response.data`/`response.status==true` with direct entity/`.success` handling. Reuse validated dummy values from `Network/Mock/MockStore+*.swift`. Build after each.

## Do-Not-Repeat

<!-- Mistakes made and corrected. Each entry prevents the same mistake recurring. -->
<!-- Format: [YYYY-MM-DD] Description of what went wrong and what to do instead. -->

- [2026-06-09] Don't bind a presented full-screen viewer's paging `scrollPosition(id:)` to the source view's own scroll `@State`. When the presentation is translucent (`.presentationBackground(.clear)`), writing that shared state on present/dismiss scrolls the source underneath → a stray push animation. Keep the viewer's paging in local `@State` and pass only a start index. [[bug-019]]
- [2026-06-09] Don't use the system `.navigationTransition(.zoom)` over a translucent/clear-background presentation. The zoom recedes the entire presenting screen and the see-through backdrop reveals it as the background "shrinking." For a hero zoom that keeps the background still, do a custom scaleEffect+offset on the element only (capture source rect via a preference) and present/dismiss the cover with `disablesAnimations`. [[bug-020]]
- [2026-06-09] `Transaction()` resolves to a project model type's `init(from:)` (compile error "missing argument for parameter 'from'"). Use `SwiftUI.Transaction()` for the SwiftUI animation transaction.
- [2026-06-10] Multiline label (`lineLimit(2)`) inside a `.fixedSize(horizontal:false, vertical:true)` row/ScrollView (or with fixedSize on the label itself) gets CLIPPED to one line / truncated. Reason: the vertical "ideal" height is computed at the text's *unbounded* width = single line, so the 2nd line never gets room. Fix: give the multiline label a deterministic box — `.frame(height: 34, alignment: .top)` (≈2 lines) — and add `.minimumScaleFactor(0.6)` so an over-long single word shrinks instead of truncating. With the label height fixed, a row-level `.fixedSize(...vertical: true)` then computes the correct cell height (badge+gap+34) and hugs it. Seen in SharePostSheet item labels (width-64 cells).
- [2026-06-28] **VideoCallTileMatrix threeLayout pitfall:** `participants[1]` always maps to the bottom-LEFT slot. The ViewModel orders participants as `[remote, local, added…]`, so local lands at index 1 → bottom-left with `showsControls: false` → no three-dots button. Fix: before passing to the matrix, move the local participant (accent == .local) to index 0 when count ≥ 3. Index 0 = full-width top slot where no controls is fine. [[bug-011]]
- [2026-06-28] **Never use geo.frame(in: .global) to pass coordinates from a deeply nested view to a top-level overlay.** The overlay's GeometryReader reports a DIFFERENT .global origin after `.ignoresSafeArea` modifiers, making the subtraction `menuAnchorFrame - geoFrame` unreliable. Use `anchorPreference(key:value:bounds)` on the source view and read with `overlayPreferenceValue` + `geo[anchor]` — SwiftUI converts the anchor to the correct local space automatically. [[bug-014]]
- [2026-06-28] **`Spacer(minLength: 0)` + `frame(maxHeight: .infinity)` in VStack fight each other:** both are flexible and SwiftUI splits remaining space equally → the content view only gets half the available height. Remove the Spacer if the content view already handles internal spacing (singleCallerInfo has its own internal Spacers). [[bug-013]]
- [2026-06-28] **`.transition()` needs a `withAnimation` context to play.** Setting `@State` without `withAnimation` triggers a view update (view appears/disappears correctly) but no transition animation fires. Always wrap the state change in `withAnimation` when a `.transition()` modifier is present on the appearing/disappearing view. [[bug-012]]
- [2026-06-10] A horizontal `ScrollView` is GREEDY on the *vertical* axis too. Stacking several in a `VStack` inside a fixed-height sheet makes them split the leftover height evenly → big even gaps between rows (looked like VStack spacing, wasn't). Fix: `.fixedSize(horizontal: false, vertical: true)` on each row's ScrollView so it hugs content height, plus a trailing `Spacer(minLength: 0)` to pin the stack to the top. Seen in SharePostSheet's contacts/media-apps/actions rows.

## Decision Log

<!-- Significant technical decisions with rationale. Why X was chosen over Y. -->

- [2026-06-15] **Clean Architecture adopted, piloted on the Profile screen.** Layers: **Domain** (`ProfileRepository` protocol + one use-case struct per operation, returning reused app models as entities and throwing `APIError` — `BaseResponse` never leaks past it) / **Data** (`ProfileRepositoryImpl` conforms to the protocol, calls the existing `ProfileService` via `Network.shared`, unwraps the envelope, updates `Storage`) / **Presentation** (`View` + `ViewModel` + `Model`; the VM takes use cases via `init` with concrete defaults — manual constructor injection, no DI container). User chose: pilot-one-feature-first, reuse existing models as entities (no DTO/Entity split + mapper), one use case per operation, manual injection. Folder shape per feature: `Screens/<Feature>/{Domain/{Repositories,UseCases},Data/Repositories,Presentation/{View,ViewModel,Model}}`. The legacy `Service/Repo/Network` stack stays — `*RepositoryImpl` wraps `*Service`, and old `*Repo` classes remain for not-yet-migrated VMs. Rollout to other features pending user approval of the pilot. [2026-06-15]
- [2026-06-10] **Photo full-screen viewer: chose system iOS 18 zoom + opaque backdrop over the custom photo-only zoom.** The custom zoom (scaleEffect/offset between captured card rect and full screen, over a translucent backdrop) was built specifically to keep the feed still while staying semi-transparent. After seeing a reference (`PhotoGallery.swift` — Apple's `matchedTransitionSource` + `.navigationTransition(.zoom)`), the user preferred the cleaner native zoom. The two are mutually exclusive: the system zoom recedes the whole presenting screen, so it only looks right with an OPAQUE detail that hides the receding feed; that means dropping the semi-transparent backdrop (the feed is no longer visible behind). User accepted that trade-off ("Native zoom, opaque"). Cost: iOS 18-only API → needs `if #available` gating + a cross-fade fallback for the 17.6 floor. Custom-zoom code (CarouselFrameKey, collapsedTransform, sourceRect plumbing) removed.

## Key Learnings (appended)
- Simulator name `iPhone 16` does not exist on this machine; use `iPhone 16 Pro` for `xcodebuild -destination`.
- Declaring an `ObservableObject` with `@Published` in a file that only `import SwiftUI` fails to build ("missing import of defining module 'Combine'"). Add `import Combine`. [2026-06-16]
- Reels overlay chrome auto-hides via `ReelCell`'s `@State chromeVisible` + a `hideTask` (2s `Task.sleep`); single tap toggles it (no longer play/pause), double tap still likes. The global tab bar hides in sync through `ReelChromeState.shared` (singleton ObservableObject in AppTabBar.swift, `@Published var tabBarHidden`); `AppTabBarView` gates the safeAreaInset bar on `!reelChrome.tabBarHidden`. Play/pause moved into a visible center control (`centerPlaybackControls`: gobackward.5 / pause-play / goforward.5, wired to skip(by: ±5)). [2026-06-16]

## Key Learnings (appended 2026-06-29 — flat button layer pattern)
- **For tappable controls overlaid on grid/tile cells, prefer a single flat layer of `.position`-ed buttons over per-cell `.overlay` buttons.** Tiles publish their button frame (in a named coordinate space, e.g. `voiceCallBody`) via a `Color.clear` GeometryReader preference; a sibling layer in that same coordinate space renders the buttons with `.position`. This hit-tests independently of the cell layout and avoids SwiftUI overlay-hit-test quirks. Caveat: a fixed flat layer does NOT scroll — for scrollable content (e.g. VoiceCallsView's >10 participant grid) keep the button in-tile instead. This reuses the same frame/anchor plumbing already used to position the popover menu (see bug-014). [2026-06-29]

## Key Learnings (appended 2026-06-29 — Network image cache concurrency)
- **`Network.shared` is a plain `final class` (not actor / not @MainActor); its `imageCache` and `inflightImages` are plain Dictionaries.** `Network.image(_:)` is called concurrently from many sites (per-tile `.task`s, `ProfileView` TaskGroup). Mutating those Dictionaries from multiple threads is a data race that can corrupt storage and HANG the app (not just crash). Fix applied: `Network.image(_:)` is now `@MainActor` and its inner fetch Task is `@MainActor`, so all cache access is serialized on main; the network `await session.data` still frees the main thread. If you add new cache state on Network, keep its access on the main actor too. [2026-06-29] (bug-022)
- **`VideoCallTileMatrix` switches view-tree branches by participant count (n==2 twoLayout / n==3 threeLayout / 4–8 adaptiveGrid / ≥9 compactGrid).** Tiles are addressed by index, so without explicit identity, changing the count tears down & rebuilds every tile and re-fires their `.task` avatar loads at once. Always render tiles via `cell(participant)` which applies `.id(participant.id)` so existing tiles are preserved within a branch and only the newcomer loads. [2026-06-29] (bug-022)

## Key Learnings (appended 2026-06-29 — CameraManager / AVCaptureSession lifecycle)
- **`CameraManager` is a per-view `@StateObject` (VideoCallView, CreateVideoView, ChatCameraView) — each builds its own `AVCaptureSession`.** Two lifecycle rules to keep it from freezing the app: (1) flip the published `isAuthorized` flag (which gates preview-layer creation) only AFTER `session.startRunning()` returns, never before `configureIfNeeded()` — attaching `AVCaptureVideoPreviewLayer.session` on main while the session is mid-`beginConfiguration` on the session queue blocks the main thread. (2) `stop()` must capture the `let session`/`movieOutput` directly, NOT `[weak self]` — on a navigation pop the `@StateObject` deallocates and a weak self is nil before the queued teardown runs, so the camera is never released and the next call's `startRunning()` hangs on hardware contention. Also added `deinit { stop() }` and `CameraPreviewView.dismantleUIView` (sets `previewLayer.session = nil`). [2026-06-29] (bug-023)

## Key Learnings (appended 2026-06-29)
- The Xcode project uses **PBXFileSystemSynchronizedRootGroup** (3 of them). New `.swift` files placed under `Binbon/` are auto-included in the target — do NOT hand-edit `project.pbxproj` to add files.
- Calls feature convention: both VoiceCall and VideoCall follow **MVVM + clean architecture** — `Data/` (Model, DataSource, Repository impl), `Domain/` (Repository protocol, UseCase), `DI/AppDIContainer+<Feature>`, `Presentation/{View,ViewModel,Components}`. Mirror this when adding a call feature.
- Call screens split state: the **ViewModel** owns media toggles, the participant roster, the call timer, raise-hand/reaction; the **View** keeps only ephemeral UI state (open sheets, popover anchors, fade timer) and geometry-dependent overlay positioning.
- The participant 3-dots menu uses a deliberate mechanism (see bug-015 history): tiles publish their button frame via a PreferenceKey (`TileButtonFrameKey`/`CallMoreMenuAnchorKey`) in a named coordinate space, and a **flat sibling button layer** in the parent renders the buttons — never a per-tile `.overlay` button (breaks hit-testing on the bottom-left cell of a 2×2 grid). Preserve this when refactoring.
- Simulator note: the Binbon scheme only exposes **iPhone 16** family simulators; `name=iPhone 16` can intermittently fail to resolve — prefer a concrete `-destination 'id=<UDID>'`.
